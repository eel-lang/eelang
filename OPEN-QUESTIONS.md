# Eel — открытые вопросы

Рабочий документ для автора, не часть релизной документации. Здесь: что уже решено, что ещё
требует решения и что будет принято по умолчанию, если автор не возразит. Находки, на
которые опираются вопросы, — в `REVIEW.md`; ссылки вида «Р §1.1» ведут туда. Как решения
ложатся на компилятор — в `REDESIGN.md`.

## Решено

1. **Записи с атомом-тегом — голые кортежи.** `('ok', v)` и `case ('ok', v):`. Ключевого слова
   `class` в языке не остаётся.
2. **`if`/`match` — операторы.** Последним оператором тела (или ветки в хвостовой позиции)
   они возвращают значение исполнившейся ветки.
3. **Parity с Gleam не нужен.** Компиляция в Abstract Erlang Format остаётся: ETF → forms →
   `compile:forms`, флаги `--erl` и `--dump-forms`.
4. **`else` в `if` не обязателен.** Чем кончается ветка, не регламентировано: присваиванием,
   вызовом, `return`. Сначала было решено «`else` обязателен», затем пересмотрено.
5. **Истинность как в Python.** Ложь — `False`, `None`, `0`, `0.0` и пустые строка, список,
   кортеж, словарь; всё остальное истинно. Понято как общее правило для `if`, guard-ов,
   фильтров comprehensions и `and` / `or` / `not`.
6. **Ранний `return` поддерживается.**
7. **Атомы остаются в одинарных кавычках.** `'ok'` — атом, `"ok"` — строка. Предложение
   «голые builtins, `from atoms import …`, `atom('…')`» снято автором.

## Открытые вопросы

### 1. `return` не последним оператором

**Решено:** настоящий ранний возврат. Как он lowering-ится — в `REDESIGN.md` §4.3.

### 2. Насколько Python-овой должна быть семантика

Главный вопрос. Пока он не решён, «подмножество Python» остаётся выражением: валидный Python
либо падает, либо молча даёт другое (Р §2). Истинность (2.1) решена — как в Python.
Остаются четыре решения:

| № | Тема | Сегодня | CPython | Рекомендую |
|---|---|---|---|---|
| 2.2 | `"a" + "b"`, `[1] + [2]` | `badarith` | конкатенация | поддержать |
| 2.3 | Сравнение разных типов: `1 < "a"` | `true` — порядок термов Erlang | `TypeError` | падение вместо ложного порядка |
| 2.4 | Переприсваивание имени, захваченного лямбдой | лямбда видит старое значение | лямбда видит новое | ошибка компиляции |
| 2.5 | Две функции с одним именем и разной арностью | две функции | побеждает последний `def` | ошибка компиляции |

- **2.1 (решено).** Каждое условие — проверка на истинность; в Erlang она выражается
  guard-выражением без вызовов функций (`REDESIGN.md` §4.7).
- **2.2.** Один диспетчеризующий хелпер: число + число, бинарник + бинарник, список + список,
  иначе `badarith`. Повторение через `*` (`"ab" * 3`) — не в этом шаге.
- **2.4.** Альтернативы: оставить и описать расхождение; изменяемые ячейки, чтобы вести себя
  как Python, — дорого и не по-BEAM-овски.
- **2.5.** Ошибка компиляции — в модуле. Переопределить функцию в следующей ячейке ноутбука,
  как в Python-REPL, остаётся можно. Вместо перегрузки по арности — параметры по умолчанию
  (`def f(x, y=0)` → `f/1` и `f/2`): синтаксис Python, естественный lowering на BEAM.
- 2.4 и 2.5 — осознанные фичи «как в Gleam»; альтернатива для обеих — оставить их и записать
  расхождение в документацию.

### 3. Что возвращает присваивание последним оператором

**Сегодня.** `def f(): x = 5` возвращает `5`; в Python — `None`.

**Варианты.**

- Функция: `nil`, как в Python, — или присвоенное значение, как сейчас.
- Ячейка ноутбука: `x = 5` печатает `5` (сейчас; так требует
  `tests/test_print.py::test_print_in_notebook`) — или молчит, как в IPython.

**Рекомендую** `nil` в функции; в ноутбуке — молчать, значение печатает только выражение.

**Последствие.** Код, полагавшийся на «все ветки присваивают одну переменную», получает
завершающее имя или `return`:

```python
def f(c):
    if c:
        r = 1
    else:
        r = 2
    r
```

### 4. Guard-ы с вычислениями

**Сегодня.** `case n if n % 2 == 0:` падает с внутренним термином Erlang (Р §1.3).

**Варианты.**

- а. Внятный отказ на этапе компиляции: перечислить, что guard может содержать.
- б. Lowering любого выражения: тело выполняется, когда guard истинен, иначе пробуются
  остальные ветки.

**Рекомендую** б: в Python `case … if` — любое выражение, а с решением про истинность guard
всё равно становится проверкой на истинность. Схема lowering-а собрана и прогнана в Erlang —
`REDESIGN.md` §4.6.

```erlang
case V of
    P1 -> case <G1 истинно> of
              true  -> B1;
              false -> <остальные ветки>
          end;
    P2  -> B2
end
```

**Цена.** Остальные ветки повторяются под каждым вычисляющим guard-ом. Вариант с именованным
`fun`, который неудачный guard вызывает снова, хуже: продолжение оказывается внутри вызова, и
хвостовой вызов теряется.

### 5. Windows

**Сегодня.** Дефолтный `eel build` и `build()` с демоном падают (Р §7).

**Варианты.**

- а. Когда unix-сокетов нет, откатываться на компилятор внутри процесса; на Windows не
  вызывать `os.kill(pid, 0)`.
- б. Дополнительно заставить build server работать на Windows: named pipes или TCP на
  localhost.
- в. Оставить: Windows — только через `--no-daemon`.

**Рекомендую** а сейчас, б — если build server нужен на Windows.

### 6. Базовые операции в этом шаге

**Сегодня.** `xs[0]`, `d['k']`, `len`, `in` и условное выражение `a if c else b` отклоняются
(Р §3).

**Варианты.**

- а. Этот шаг — только то, что перечислено в «Решено», и исправления из ревью.
- б. Добавить и минимальный набор.

**Рекомендую** а; набор — следующий шаг, где каждая операция сразу проектируется с семантикой
Python.

### 7. Импорты и константы на уровне модуля

**Сегодня.** `from x.y.z import my_fun` работает. Не работает всё остальное (проверено):

- константа на уровне модуля: `MAX = 3` → `only def/class/from…import are allowed at the
  top level`; `from cfg import MAX` → `name 'MAX' is not defined`;
- `import x` и `import x as y` → `plain import X is not supported`;
- изменившийся модуль не пересобирает зависимые (Р §5.1), импортируемые имена не проверяются;
- `from lists import reverse` работает, но в документах не описано.

**Варианты.**

- а. Константы, `import x as y`, пересборка зависимых входят в этот шаг.
- б. Только пересборка зависимых и проверка имён; константы — вместе с базовыми операциями.

**Рекомендую** б: пересборка зависимых — исправление дефекта, остальное — новые возможности.

## По умолчанию, если автор не возразит

- [ ] **Правило атомов уточняется** (решено только «атомы в одинарных кавычках»): литерал с
  префиксом (`r'ok'`, `u'ok'`) и в тройных кавычках (`'''ok'''`) — строка; неявная склейка с
  разными кавычками (`'a' "b"`) — ошибка компиляции. Сегодня `'''ok'''` — атом, `'a' "b"` —
  атом `ab` (Р §4).
- [ ] **Код после `return`** — ошибка компиляции; в Python он молча мёртвый.
- [ ] **`if` без `else` последним оператором** возвращает `nil` на пути без `else` (в Python —
  `None`).
- [ ] **`return` в ячейке ноутбука** — ошибка, как в Python.
- [ ] **Прелюдия `Ok`/`Error` уходит**: вместо `Ok(1)` — `('ok', 1)`.
- [ ] **`match receive():` и `Timeout` остаются**, но имена явно зарезервированы: своё
  `Timeout` или `receive` — ошибка компиляции, а не молчаливый перехват.
- [ ] **Область видимости как в Python**: присваивание в ветке видно после неё. Переменная,
  присвоенная не во всех ветках и не связанная раньше, — ошибка компиляции (в Python это
  `UnboundLocalError` на рантайме).
- [ ] **Or-паттерны могут связывать имена**, если все альтернативы связывают одни и те же:
  `case ('ok', v) | ('error', v):`.
- [ ] **`match` без сработавшей ветки** по-прежнему роняет процесс.
- [ ] **Инкрементальная сборка** пересобирает зависимые модули.
- [ ] **Build server**: исправляются падение на ушедшем клиенте (Р §5.2–5.3) и устаревший
  компилятор (Р §5.4).
- [ ] **`and` / `or` возвращают операнд, `not` — boolean**, как в Python.
- [ ] **REPL печатает значения синтаксисом eel** (`'ok'`, `"hi"`, `(1, 2)`, `{'a': 1}`), а не
  терминами Erlang.
- [ ] **Документы, ноутбук и тесты** переписываются под новые правила; упоминания Gleam
  уходят.

Архитектурные предложения — рантайм `eel_rt`, диспетчер раннего возврата, ядро ноутбука,
build server на TCP — вынесены в `REDESIGN.md`; каждое можно принять или отвергнуть отдельно.
