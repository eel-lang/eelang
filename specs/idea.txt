I am going to build Gleam with Python syntax and call it eel. File extension: `.eel`.

**The idea**

For static analysis, use a forked Python static analyser (for example a Kotlin one, for PyCharm).
For compilation, use the Python package and the Python parser — because eel's syntax matches
Python's. Over time we will support syntax beyond Python's (pattern matching, pipelines), but for
now (milestone 1) it is plain Python syntax.

**No mutating operations**

The syntax is Python's, minus the mutating operations. For example, `for` loops are dropped.
A variable may be reassigned: `x = x + 1`. Variable names map to Erlang the same way as in Gleam.

For example, working with lists and dicts:

head, *rest = my_list
my_map |= {'key': 'value'}

**Imports** are hierarchical, with Python syntax for them:

from my.custom.pak import my_fun

Gleam does it the same way.

**if, case**

Eventually it will look like this:

value =
  if condition:
    a
  else:
    b

val = match expr:
  case expr1:
    do_first()
  case expr2:
    do_second()

But for now we use Python's syntax:

if condition:
  value = a
else:
  value = b

match expr:
  case expr1:
    val = do_first()
  case expr2:
    val = do_second()

The compiler checks that the last operation is an assignment and that the same variable is assigned.

**Let it crash**

This concerns the match operator. One of the variants must match — otherwise it is a runtime error and
the process crashes. This is how eel differs from Gleam, where the compiler refuses to compile such
code and forces you to enumerate all variants in the case.

**Pattern matching**

For now — through match..case. In the longer term — `let MyPattern = Expr`.

**Atoms**

Through single quotes: `'ok'`.

Instead of atoms, types are recommended — the same as in Gleam. They are defined roughly like this
(all names are there to explain the scheme):

class CustomType(AtomPrefixed):
  x: int
  y: int

match val:
  case CustomType(x, y):
    result = (x, y)

This is equivalent to:

match val:
  case ('custom_type', x, y):
    result = (x, y)

Besides that, there can be types like these (also for the scheme):

class CustomRecord(NativeRecord):
  x: int
  y: int

NativeRecord is the native OTP 29 record that does not lose its type at runtime.

class CustomMap(Map):
  x: int
  y: int

**Implementation language**

It is Python. In the future some parts are planned to be implemented in spy (static python).

Important: although reusing Gleam's code is not planned for now, the abstractions must be the same —
at least at the very lowest level, which generates abstract Erlang. Code for identical syntax nodes
must be generated identically. Code must be generated into the Abstract Erlang Forms, just like in
Gleam.
