# Eel — критическое ревью

Рабочий документ для автора, не часть релизной документации. Описывает дерево на коммите
`45e2107` (25.11.2026); переделка тестов описана в §9.2. Решения, принятые после ревью, и
оставшиеся вопросы — в `OPEN-QUESTIONS.md`; архитектура, которую я предложил бы с нуля, — в
`REDESIGN.md`.

**Как делалось.** Прочитано всё дерево. Каждый дефект ниже воспроизведён запуском —
компилятора, CLI, build server или хука ноутбука — на Windows (Python 3.15.2,
OTP 29 / ERTS 17.1.2, Gleam 1.19.2) и в Linux-контейнере с теми же версиями. Что только
прочитано и не запускалось, отмечено в тексте и собрано в §13. У каждого дефекта приведены
вход и наблюдаемый результат, чтобы его можно было повторить руками.

## Вердикт

Eel — аккуратно собранный прототип. Цепочка «исходник → IR → abstract forms →
`compile:forms`» чистая, формы сверены с Gleam, стек-трейсы указывают на строки `.eel`,
хвостовые вызовы сохраняются (10 млн рекурсивных шагов проходят), 202 теста на Linux
зелёные.

Но язык пока не «Python с ограничениями», а язык с синтаксисом Python и семантикой Erlang:
обычный Python-код либо не компилируется, либо молча работает иначе. Инфраструктура сборки
падает в реалистичных ситуациях, дефолтный путь сборки не работает на Windows. Дорожная
карта «подмножество Python без дополнительных фич» решает часть этого, но её три решения
оставляют открытым главный вопрос — насколько Python-овой должна быть семантика.

## 1. Компилятор: что встречает обычный Python

### 1.1. `return` не в хвосте молча выбрасывается

```python
def f(x):
    return 1
    print(x)
    2
```

Компилируется в `f(X) -> 1, eel_print(X), 2.` Вызов `m:f(7)` напечатал `7` и вернул `2`.
CPython возвращает `1` и ничего не печатает. Ни ошибки, ни падения.

Где: `eel/frontend.py:439–441` — любой `return` превращается в обычный оператор-выражение.

Внутри `if`/`match` не в хвостовой позиции `return` отклоняется, но сообщение не о нём:
`branch must end with an assignment to the same variable` (`eel/backend.py:856–858`).

### 1.2. `if` не может быть оператором

```python
def f(x):
    if x > 0:
        print('positive')
    x
```

Результат: `eel: src/m.eel:2: if without else has no value on the false path`.

- С `else`, который тоже только печатает: `branch must end with an assignment to the same
  variable`.
- С `else: pass` — снова первое сообщение.

`if`, который только действует, возможен лишь как последний оператор тела.

Где: `eel/frontend.py:444–447` (`else` обязателен), `eel/backend.py:841–859` (каждая ветка
должна кончаться присваиванием).

### 1.3. В guard-е нельзя ничего вычислять

| Guard | Сообщение |
|---|---|
| `case n if n % 2 == 0:` | `erl_lint: {illegal_guard_local_call,{eel_mod,2}}` |
| `case n if n ** 2 > 4:` | `erl_lint: {illegal_guard_local_call,{'_eel_pow',2}}` |
| `case n if n // 2 == 0:` | `erl_lint: {illegal_guard_local_call,{eel_floordiv,2}}` |
| `case n if positive(n):` | `erl_lint: {illegal_guard_local_call,{positive,1}}` |
| `case ys if ys.count(1) > 0:` | `erl_lint: illegal_guard_expr` |

Пользователь видит внутренние имена хелперов. В Python `case … if` допускает любое
выражение.

Где: guard генерируется как есть — `eel/backend.py:545`, `:632`, `:767`, `:819`; неизвестные
ошибки линтера печатаются термином — `eel/eel_compile.escript:223–224`.

### 1.4. Синтаксическая ошибка Python — не ошибка компиляции

Опечатка в `.eel` (`def f(x):` и `x +`):

- Windows: traceback, последняя строка `SyntaxError: invalid syntax` — без файла и строки;
- Linux, дефолтный путь через build server: `eel: internal build server error (see log)` —
  тоже без файла и строки.

Оба выхода — с кодом 1. Это нарушает контракт из `specs/SPEC.md:20–21` («`eel: <path>:<line>:
<text>`, без traceback»).

Где: `eel/frontend.py:73` (`ast.parse` без обработки), `eel/compiler.py:46–56` (ловится
только `EelError`), `eel/server.py:57–60` (любое другое исключение становится «internal»).

### 1.5. Магические имена

- **`receive` не переопределяется**, хотя `specs/architecture.md:164–167` говорит обратное.
  `def receive(x): x + 1` и затем `receive(1)` дают `receive takes no arguments (use `case
  Timeout(ms):` for a timeout)`. То же с параметром: `def f(receive): receive(1)`.
  `f = receive` даёт `name 'receive' is not defined`. Где: `eel/frontend.py:685–690`.
- **Пользовательский класс `Timeout` нельзя сматчить на сообщении.** `match receive():` с
  `case Timeout(ms):` даёт `Timeout expects a value in milliseconds`: любой паттерн
  `Timeout(...)` перехватывается. Где: `eel/frontend.py:529–544`, вызов на `:460`.
- **Функция с именем `Ok` или `Error` — мёртвый код.** `def Error(e): 'wrapped'` и затем
  `Error(x)` возвращают `{error,1}` — кортеж прелюдии. Предупреждения нет. Где:
  `eel/frontend.py:691` — проверка конструктора идёт раньше разрешения вызова.
- **Вызов модуля по имени**: `lists.reverse(xs)` даёт `name 'lists' is not defined`, а
  `specs/architecture.md:96–97` утверждает, что импорт для этого не нужен.
- При этом `from lists import reverse` работает и даёт `[3,2,1]`: стандартная библиотека
  Erlang доступна через Python-синтаксис импорта. В документах этого нет, импортируемые
  имена никак не проверяются.

### 1.6. Каталог без `src/` собирается успешно

`python -m eel build <dir>` выходит с кодом 0, не печатает ничего и записывает
`build/dev/erlang/<dir>/ebin/<dir>.app` с пустым `modules`. На обеих платформах.

Где: `eel/compiler.py:362` — `glob` по несуществующему каталогу просто пуст.

### 1.7. Литералы на границах

- `1e400` даёт `eel: cannot decode forms`: без файла и строки, и причина названа неверно —
  `eel/eel_compile.escript:154–157` объявляет «ошибкой декодирования» любое исключение между
  `binary_to_term` и компиляцией.
- Целочисленный литерал из 700 цифр даёт сырой `ValueError: bytes must be in range(0, 256)`.
  Где: `eel/etf.py:60–64` — длина большого целого должна помещаться в байт, большее не
  проверяется.

## 2. Валидный Python, который даёт другой результат

Один и тот же исходник прогнан CPython 3.15 и eel (OTP 29).

Сначала то, что проходит без ошибки, но иначе:

| Выражение | CPython | eel |
|---|---|---|
| `x = 1; f = lambda: x; x = 2; f()` | `2` | **`1`** |
| `def arity(x)` и `def arity(x, y)`; затем `arity(9)` | `TypeError` | **`1`** |
| `(1 == "a", 0 == False, 1 == True, [] == (), 'a' == "a")` | `(False, True, True, False, True)` | **`{false, false, false, false, false}`** |
| `(1 < "a", 'zzz' < "a", [1] < (1,))` | `TypeError` | **`{true, true, false}`** |
| `match [1]: case y if y:` | `1` | **`0`** — guard молча не срабатывает |
| `[x for x in [1, 2] if x]` | `[1, 2]` | **`[]`** |

Затем то, на чём eel падает:

| Выражение | CPython | eel |
|---|---|---|
| `if xs:` на `[1]` и на `[]` | ветка выполняется / не выполняется | `{case_clause,[1]}`, `{case_clause,[]}` |
| `1 and True`, `[] and False`, `1 or 2` | операнд | `{badarg,…}` |
| `not 5` | `False` | `{badarg,…}` |
| `"a" + "b"`, `[1] + [2]` | `'ab'`, `[1, 2]` | `{badarith,…}` |
| `True + 1` | `2` | `{badarith,…}` |
| `[c for c in (1, 2)]`, `[c for c in "abc"]` | `[1, 2]`, `['a', 'b', 'c']` | `{bad_generator,…}` |

Первая группа хуже второй: «молча иначе» не предупреждает ни компилятор, ни инструменты
Python. Часть расхождений закреплена тестами как желаемое поведение:
`tests/test_nested_defs.py::test_module_semantics` (`captured()` ожидает `2`) и
`tests/test_values.py::test_filter_non_bool_skips`.

`README.md:87` обещает «`==` ведёт себя как Python»; это верно только для чисел.

## 3. Чего в подмножестве нет

| Запись | Сообщение |
|---|---|
| `xs[0]`, `d['k']` | `unsupported expression Subscript` |
| `len(xs)`, `str(x)`, `reversed(xs)`, `sorted(xs)`, `max(a, b, c)` | `function len/1 is not defined` и тому подобное |
| `a if b else c` | `unsupported expression IfExp` |
| `0 < x < y` | `comparison chains are not supported yet` |
| `x in y` | `comparison operator (is/in/…) is not supported` |

Без индексации и `len` на списках и словарях почти ничего нельзя сделать.

## 4. Атомы через кавычки

Атом отличается от строки только кавычками (`'ok'` против `"ok"`), которые Python считает
несущественными.

**Форматировчик ломает программу молча.** Black 26.10.1 на образце `.eel` переписал `'ok'`,
`'error'` и `'done'` в `"ok"`, `"error"` и `"done"` — атомы стали строками.

**Правило непоследовательно.** Решает первый символ в позиции литерала
(`eel/frontend.py:607–611`, `:300–315`):

| Запись | Результат |
|---|---|
| `'ok'` | атом |
| `'''ok'''` | атом |
| `'a' "b"` — неявная склейка | атом `ab` |
| `r'ok'`, `u'ok'` | строка |
| `"a" 'b'` | строка `"ab"` |

В Python все шесть записей дают одну и ту же строку.

## 5. Сборка: CLI, инкрементальность, build server

### 5.1. Инкрементальная сборка не знает о зависимостях

Модуль `a` делает `from b import f`. После переименования `f` в `h` в `b.eel` вторая сборка
выходит с кодом 0 и без сообщений; пересобран только `b.beam`, `a.beam` не тронут. Вызов
`a:g()` на рантайме даёт `{'EXIT',{undef,[{b,f,[],[]},…`. Кросс-модульной проверки нет вовсе,
манифест хранит только хеш самого модуля.

Где: `eel/compiler.py:319–329`, `:360–383`.

### 5.2. Build server падает, если клиент ушёл, не дождавшись ответа

Сервер однопоточный (`eel/server.py:63–87`): соединение, которое ничего не присылает,
блокирует его целиком. Ping ждёт 2 с и закрывает сокет. Когда сервер до него добирается и
отвечает, `conn.sendall` (`eel/server.py:84`) кидает `BrokenPipeError: [Errno 32] Broken
pipe`. Исключение не ловится, `finally` останавливает демона, сервер выходит.

Наблюдение: молчащее соединение → `ping()` даёт `None` через 2.0 с → после его закрытия
сервер уже не отвечает; в системе 0 серверов и 0 демонов.

### 5.3. Долгая сборка и второй клиент оставляют висячий процесс

Сборка 1200 модулей занимает 5.7 с. Через 0.7 с после её старта приходит второй клиент:

1. `ping()` даёт `None` через 2.0 с.
2. `ensure()` поднимает второй сервер и второй демон, без блокировки
   (`eel/client.py:113–120`). В системе 2 сервера и 2 демона.
3. Первый сервер отвечает первому клиенту, затем падает на брошенном ping (§5.2). По коду
   (`eel/server.py:123–130`) его `finally` останавливает демона через общий сокет-файл и
   удаляет сокет-файл и pid-файл второго сервера.
4. `eel daemon stop` и `daemon status` печатают «not running», а процесс второго сервера
   живёт и недостижим.

### 5.4. Сервер не замечает правки компилятора

Отпечаток исходников кэшируется на жизнь процесса (`eel/compiler.py:39`, `:64–73`), сам код
загружен в память, таймаута простоя нет. После правки `eel/compiler.py` даже `--force` через
сервер выдал старый результат: версия приложения `0.1.0` вместо `9.9.9`. Свежий процесс дал
новый. Для разработчика компилятора каждый `eel build` после правки идёт старым кодом; то же
после обновления пакета.

## 6. Ноутбук

- **Пустая ячейка выполняет предыдущую повторно.** У пустой (или из одних пробелов) ячейки
  IPython не вызывает `pre_run_cell`, а `post_run_cell` берёт исходник из `state["raw_cell"]`,
  где остался предыдущий (`eel/notebook.py:62–66`). Наблюдение: пустая ячейка напечатала
  результат предыдущей; из хуков сработал только `post`.
- **Ошибки не помечают ячейку как упавшую.** Они пишутся в stderr, `result.error_in_exec` не
  выставляется: в перепроигранном туре все шесть «сломанных» ячеек формально выполнены
  успешно.
- **Сохранённые выводы в `eel.ipynb` устарели.** Ячейка с операторами хранит
  `eel runtime error: {error,undef}`, реально даёт `{3.5,3,-4,1,1024,0.5,true,true}`. Ячейки
  с паттерном класса и с цепочкой декораторов не хранят вывода, хотя дают `{1,2}` и `3`.
  Строк `erl: …` у comprehensions в сохранённых выводах нет.
- **Kernelspec не существует.** Метаданные ноутбука называют ядро `eel` («Eel (ee1)»).
  Репозиторий его не поставляет: `eel/notebook.py` подключается расширением IPython, и
  `specs/notebook.txt` говорит «без своего ядра».

## 7. Windows

- В Python 3.15.2 под Windows нет `socket.AF_UNIX`. Дефолтный `eel build` и `build()` с
  демоном падают с traceback в `eel/client.py:51`, код 1. `--no-daemon` работает.
- `eel/client.py:123–128` вызывает `os.kill(pid, 0)`. По документации Python, на Windows
  любое значение сигнала, кроме консольных событий, безусловно завершает процесс. Не
  запускал.
- В README нет ни слова о платформах.

## 8. Качество кода

- **Дубли в `eel/backend.py`.** `stmt_form`, `def_form` и `_nested_def_form` определены
  дважды одинаково (`:556` и `:693`, `:574` и `:711`, `:595` и `:732`). `_case_value`
  определён дважды по-разному: `:659` — мёртвый, `:794` — живой. `_receive_build` (`:622`) и
  `_receive_form` (`:759`) — две параллельные реализации одного `receive`. Около 130 строк;
  Python молча берёт последнее определение.
- **Библиотека хелперов написана дважды**: формами в `eel/backend.py:1328–1580` и вручную на
  Erlang в `eel/repl.escript:78–143` — десять функций. Сейчас они совпадают; ничто не
  проверяет, что так будет и дальше.
- **Три lowering-а декораторов**: `persistent_term` плюс `-on_load` для функций модуля,
  словарь процесса плюс плейсхолдер для ноутбука, немедленное применение для вложенных `def`.
- **`Session` управляет генератором через приватные поля**: `eel/session.py:19–21`, `:33–34`,
  `:42`.
- **Качество сообщений**: `internal build server error`, `cannot decode forms`, термины
  `erl_lint`, `name 'lists' is not defined` для вызова модуля.
- `eel/eel_compile.escript:201–204` печатает ошибки только первого не собравшегося модуля.
  По чтению.
- **Версии расходятся**: `pyproject.toml` — `0.3.0`, `eel/__init__.py:3` — `0.1.0`, версия
  приложения в `.app` — зашитые `0.1.0` (`eel/compiler.py:404`).
- **Нет линтера и нет CI**: конфигураций ни того, ни другого в репозитории нет. Дубли в
  `eel/backend.py` — прямое следствие.

### 9.2. Что сделано, чтобы набор шёл на обеих платформах

Изменён только каталог `tests/`:

- `tests/platform_support.py` — `cli_build()` и `build()` идут дефолтным путём там, где есть
  unix-сокеты, и через `--no-daemon` / `daemon=False` на Windows. На Linux поведение не
  изменилось.
- Тесты build server и демона помечены `needs_unix_sockets`; на Windows они пропускаются.
- Пути внутри `erl -eval` (`tests/test_etf.py`, `tests/test_parity.py`) переведены на
  `as_posix()`: обратный слэш Erlang читал как escape.
- Ожидаемый путь в сообщении об ошибке строится через `pathlib.Path` — родной разделитель
  платформы.

Ограничение: на Windows проверяется только путь «escript внутри процесса» (§7).

### 9.3. Слабые места

- Вакуумные ассерты: `tests/test_values.py::test_semantics_in_erl` проверяет
  `assert "1" in out.stdout`.
- Нет skip при отсутствии `erl` или `gleam`: без них тесты падают с `TypeError`, а не
  пропускаются.
- Тесты закрепляют расхождения с Python как желаемые (§2).
- Не покрыто: синтаксические ошибки Python, `return` не в хвосте, guard-ы с вызовами,
  изменения в импортируемых модулях, пустая ячейка ноутбука.
- `.pytest_cache/` нет в `.gitignore`. Прогон из корня репозитория оставляет и
  `erl_crash.dump` — он в `.gitignore` есть.

## 11. Дорожная карта

После ревью автор принял шесть решений; полный список — в `OPEN-QUESTIONS.md`. Первые три —
про устройство языка.

**1. Вместо классов — голые кортежи.** `('ok', v)` и `case ('ok', v):` вместо
`class Ok(AtomPrefixed)`, `Ok(v)` и `case Ok(v):`.

Убирает обе не-Python-овые конструкции сразу: объявление с чужим базовым классом и
присваивание с паттерном `Ok(value) = my_fun()` — единственную конструкцию, которая даже не
парсится как Python. Что удаляется:

- `eel/frontend.py:166–297`: `rewrite_pattern_assignments`, `_as_pattern_assign`,
  `_expr_to_pattern`, `_check_pattern_names`;
- `eel/frontend.py:111–163`: `_collect_classes`, `_class_fields`, `_base_name`; константы
  `BUILTIN_CLASSES`, `BASE_CLASS`, `PATTERN_MARKER` — на `:42–49`; ветки конструктора и
  `MatchClass` в `_expr` и `_match_pattern`;
- `eel/notebook.py:51–53`, `:97` — input transformer для ноутбука;
- `eel/session.py:95–118` — `_class`;
- тесты на классы и на присваивание с паттерном в `tests/test_values.py`,
  `tests/test_notebook.py`;
- `specs/patterns.md` (раздел о присваивании с паттерном), `specs/goal-and-requirements.md`,
  `specs/architecture.md`, README, «Stage 5» в `eel.ipynb`.

Что теряется: проверка арности (кортеж не той длины — просто «не совпало»), тег, выводимый
из имени класса, прелюдия `Ok`/`Error`. Опечатка в теге не ловится, а в селективном
`receive` означает вечное ожидание.

**2. `if`/`match` — операторы; последними в теле они возвращают значение.** Оператор
`if`/`match` ничего не возвращает; последним оператором тела он возвращает значение
последнего оператора исполнившейся ветки.

Это самый большой структурный шаг, больше удаления классов. Правило «одна переменная во всех
ветках», двойной lowering (хвостовая и не-хвостовая позиция) и фейковый `return` существуют
только потому, что `if`/`match` сейчас — «выражения без синтаксиса выражений». Вместе с
правилом уходят ошибки из §1.2 и дубли из §8.

**3. Parity с Gleam не нужно, компиляция в abstract Erlang нужна.** Parity был загрузочным
оракулом: он помог поставить генератор форм и заодно закрепил семантику Erlang в операторах —
то, из-за чего eel не похож на Python. Оракулом остаются обычные тесты форм. Удаляются
`tests/test_parity.py`, `tests/erl_term.py`, зависимость от `gleam` и упоминания в README,
`specs/` и «Stage 8» тура.

**4. `else` в `if` не обязателен.** Сначала было решено «обязателен», затем пересмотрено.

**5. Истинность как в Python** — ложь это `False`, `None`, `0`, `0.0` и пустые строка, список,
кортеж, словарь.

**6. Ранний `return` поддерживается.**

Решения 4–6 снимают находки §1.1, §1.2 и первую группу §2. Как они ложатся на компилятор — в
`REDESIGN.md`.

Дорожная карта этим не исчерпывается: атомы, `match receive():`, `Ok`/`Error`, операторы —
в `OPEN-QUESTIONS.md`.
