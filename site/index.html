What Eel aims for

Eel is inspired by Gleam, but its goals and founding principles differ in a few important ways.

01

Great IDE support

static analysis, first-class

A great static-analysis experience in the IDE is one of the goals — and the main target is PyCharm.

02

Great stdlib

batteries, with methods

A stdlib that is pleasant to use, with OOP-style methods on the core data structures.

dic.get(my_key)
my_list.map(my_func)
name.startswith(prefix)
03

Optional static typing

never mandatory

Static typing is fully optional. When you reach for it, it is there to make the code clearer and more expressive.

04

All data types equally

no second-class data

Maps, records, native records and the rest get the same level of support — and optional types make all of them convenient.

map · record · native record
05

OTP first-class

not an afterthought

Working with OTP matters as much as a good standard library.

06

Python-friendly

BEAM ↔ CPython

One of the tasks is to bring the BEAM and CPython ecosystems closer, and to enable projects like Hornbeam.

The syntax you need,
baked into Python.

Every construct below is compiled, not interpreted: the compiler turns this Python into Erlang abstract forms. Pick a category and read the code.

Quotes decide the type. Tuples, lists and dicts keep their Erlang shapes.

values.eel 
def pair():
    ('ok', "ok", (1, 2), [1, 2], {'k': 1})
# {ok, <<"ok">>, {1, 2}, [1, 2], #{k => 1}}

Arithmetic keeps Python's semantics; booleans compile to andalso and orelse.

operators.eel 
def calc(a, b):
    (a // b, a % b, a ** 2, a == b, not (a < b))

match is an expression: every branch assigns the same variable.

control.eel 
def classify(n):
    match n:
        case 0:
            r = 'zero'
        case _ if n < 0:
            r = 'negative'
        case _:
            r = 'positive'
    r

Destructuring, constructor patterns and guards compile to real Erlang patterns.

patterns.eel 
def first_two(xs):
    a, b, *rest = xs
    (a, b)

def swap(p):
    match p:
        case (x, y):
            q = (y, x)
    q

def, lambda and closures — and arity is part of a function's identity.

functions.eel 
def twice(f, x):
    f(f(x))

def bump(n):
    twice(lambda x: x + 1, n)

A class compiles to a tagged tuple, and its constructor is inlined.

classes.eel 
class Point(StartingWithAtom):
    x: int
    y: int

def shift(p, dx):
    match p:
        case Point(x, y):
            q = Point(x + dx, y)
    q

List and dict comprehensions become Erlang comprehensions, filters included.

comprehensions.eel 
def evens(xs):
    [x * 2 for x in xs if x % 2 == 0]

def by_id(pairs):
    {k: v for k, v in pairs}

The module is the path; imports are Python imports with Gleam's rules.

modules.eel 
from my.app.math import add, mul as times

def total(a, b):
    times(add(a, b), 2)

OOP-styled standard library

planned surface · not in the compiler yet

Strings

  • name.startswith(prefix)prefix test, bytes included
  • name.strip()trim whitespace on both ends
  • line.split(sep)split into a list of strings
  • path.replace(from, to)replace every occurrence
  • sep.join(items)join a list back into one string

Lists

  • xs.map(f)apply a function to every element
  • xs.filter(pred)keep the elements that match
  • xs.fold(acc, f)reduce to a single value
  • xs.take(n)the first n elements
  • xs.zip(ys)pairs, like Python's zip

Maps

  • config.get(key)value or nil, never an exception
  • m.put(key, value)a new map, the old one intact
  • m.merge(other)what |= compiles to
  • m.keys()keys, in no particular order
  • m.items()pairs, for comprehensions

This is an early alpha.
The code is 100% vibe-coded.

It compiles real modules today, and it is not something you put in production yet. The honest list of what that buys you and what it costs:

plus

  • + A small codebase you can fork the compiler is a handful of Python modules: read it in an afternoon, fork it, and bend it to your own project.

minus

  • − No type checker annotations are documentation. Eel does not check them; outside tools own that, as in Python.
  • − No static analysis yet the IDE experience is a goal, not a feature: the analyzer is planned, and PyCharm support does not exist today.
  • − The standard library is a sketch OOP-style methods on the core types are designed, not implemented; today you work with bare Erlang forms.
  • − Pre-release, nothing to install runs from a checkout on Python 3.15 and OTP 29: no package, no versioned releases, no stability promise.
  • − Written with AI, end to end expect uneven code, thin tests in places and APIs that move. The parity suite with Gleam is the part that keeps it honest.
