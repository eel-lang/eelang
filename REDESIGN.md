# Eel — архитектура с нуля

Рабочий документ для автора, не часть релизной документации. Ответ на вопрос «что я сделал
бы иначе, если бы писал проект с нуля». Опирается на находки `REVIEW.md` и решения из
`OPEN-QUESTIONS.md`.

Решения автора приведены как данность и отмечены словом «решено». Всё остальное — мои
предложения: их можно отвергнуть по одному, архитектура от этого не рассыпается. Схемы
lowering из §4 собраны и прогнаны в Erlang вручную, до написания этого текста.

## 1. Что я сделал бы иначе

Три вещи важнее остальных.

1. **Один механизм управления вместо двух.** Сейчас тело функции генерируется двумя
   способами — для хвостовой и не-хвостовой позиции — и в обоих тащит правило «одна
   переменная во всех ветках». Отсюда половина сложности `eel/backend.py`, его дубли и
   фейковый `return`. С нуля — один механизм из трёх понятий: окружение, соединение,
   «проваливается ли управление» (§4).
2. **Один рантайм.** Хелперы (`mod`, `pow`, `print`, `iter`…) сегодня генерируются формами в
   каждый модуль и второй раз написаны руками в `eel/repl.escript`. С нуля — один модуль
   `eel_rt` на Erlang (§5).
3. **Оракул — CPython, а не Gleam.** Раз язык — подмножество Python, проверка та же: одна и
   та же программа под CPython и под eel обязана дать один и тот же результат (§9).

Остальное — в таблице.

| Область | Сейчас | С нуля |

| Разрешение имён | по ходу генерации; три изменяемых словаря, сохранение и восстановление в семнадцати местах | окружение передаётся явно и не изменяется; генератор — чистая функция |

## 2. Границы языка

**Синтаксис** — подмножество Python, разбирается штатным `ast.parse`. Два исключения, и оба
нужно перечислить в документации явно:

- атом записывается в одинарных кавычках: `'ok'`;
- `match receive():` — селективный receive, `Timeout(ms)` — его ветка таймаута. Оба имени
  зарезервированы.

**Записи** — голые кортежи с атомом-тегом (решено): `('ok', v)`, `case ('ok', v):`. Ключевого
слова `class` нет.

**Управление** (решено):

- `else` в `if` не обязателен; чем кончается ветка, не регламентировано — присваиванием,
  вызовом, `return`;
- `if`/`match` — операторы; последними в теле они возвращают значение исполнившейся ветки;
- ранний `return` поддерживается;
- истинность как в Python: ложь — это `False`, `None`, `0`, `0.0` и пустые строка, список,
  кортеж, словарь; всё остальное истинно. Правило общее для `if`, guard-ов, фильтров
  comprehensions и `and` / `or` / `not`.

Необязательный `else` ничего не стоит генератору: отсутствующая ветка — это ветка, которая
проваливается, ничего не изменив (§4.3). Правило «ветка должна кончаться присваиванием» не
нужно: оно запрещало бы ветки, которые только действуют, и ранний `return`.

**Чего в языке нет** — моё предложение: циклы (рекурсия), классы, множества, исключения,
f-строки, `import X`. Базовые операции (`xs[0]`, `len`, `in`, условное выражение) — отдельный
шаг (вопрос 6 в `OPEN-QUESTIONS.md`).

## 3. Конвейер

```
исходник .eel
   │  токены: правило атомов          ast.parse: SyntaxError → EelError
   ▼
Python AST ──► IR: десахаринг, нормализация хвостов
                  │
                  ▼  генератор (чистая функция): окружение, соединение, выход блока
               abstract forms ──ETF──► compile:forms ──► .beam
```

IR остаётся деревом без типов, как сейчас. Добавляются две вещи, которых нет:

- **нормализация** во frontend: хвостовые `return` (§4.1), `elif` → вложенный `if`;
- **генератор без состояния**: всё, что ему нужно, приходит параметрами.

## 4. Ядро: окружение, соединение, выход блока

### 4.1. Хвосты становятся `return`

Frontend приводит каждое тело функции и вложенного `def` к виду «заканчивается `return`»:

- последнее выражение `e` → `return e`;
- последний `if`/`match` → то же для каждой ветки;
- иначе в конец дописывается `return None`.

Благодаря этому у генератора нет «хвостового режима»: тело всегда заканчивается `return`,
и `case` последнего ветвления естественно оказывается значением функции. Ячейка ноутбука
нормализуется так же; её `return` и есть напечатанное значение.

### 4.2. Блок

Блок — последовательность операторов. Его генерация возвращает пару **(формы, выход)**, где
выход один из двух:

- `RET` — каждый путь блока заканчивается `return`;
- `FALL(env)` — есть путь до конца блока, и на нём окружение равно `env`.

**Окружение** — неизменяемое соответствие «имя Python → переменная Erlang» и множество имён,
захваченных лямбдами. Присваивание не меняет окружение, а создаёт новое с очередной версией
имени: `x` → `X` → `X@1` → `X@2`. Номера не переиспользуются.

Эскиз:

```python
def gen_block(stmts, env, sink) -> (forms, exit):
    forms = []
    for s in stmts:
        match s:
            case Return(e):
                return forms + [expr(e, env)], RET
            case Assign(t, v):
                forms += [match_form(t, expr(v, env), env)]
                env = env.bind(t)
            case Expr(e):
                forms += [expr(e, env)]
            case NestedDef(f):
                forms += [bind(f, env)]
                env = env.bind(f.name)
            case If(...) | Match(...):
                return forms + gen_branch(s, stmts.after(s), env, sink)
    return forms, FALL(env)
```

Сравните с `_Gen` в `eel/backend.py`: там состояние — поля объекта, и его сохраняют и
восстанавливают вручную. Здесь состояние — параметр и результат.

### 4.3. Ветвление

Пусть после `if`/`match` есть ещё код (`rest`). У каждой ветки генерация даёт выход. Дальше
три случая.

1. **Ни одна ветка не проваливается.** Обычный `case`; его значение — значение функции.
   `rest` недостижим и выбрасывается.
2. **Проваливаются все, и ни в одной нет `return`.** Ветки заканчиваются кортежем из имён,
   изменившихся в ветке: `K = case … end`. Затем `rest` генерируется один раз.
3. **Иначе.** Ветки возвращают `{ret, V}` или `{join, K}`, а диспетчер один раз запускает
   `rest`:

   ```erlang
   case case Условие of
           true  -> {ret, V};
           false -> {join, K}
       end of
       {ret, V}  -> <sink>;
       {join, K} -> <rest>
   end
   ```

   `<sink>` — это «как здесь покинуть функцию»: на верхнем уровне тела — `V`, внутри ветки
   ветвления с диспетчером — `{ret, V}`, чтобы возврат дошёл до своего диспетчера.

Почему третий случай нужен: в Erlang нет `return`, а код после `case` выполняется для всех
веток. Копировать `rest` в каждую ветку нельзя — цепочка из n операторов `if` даст 2^n копий.
Диспетчер обходит это ценой одного кортежа на ветвление с ранним возвратом.

Хвостовой вызов сохраняется: `rest` стоит в хвосте ветки диспетчера. Проверено: `loop(N)`,
написанный с ранним `return` и диспетчером, проходит 10 млн шагов.

`if` без `else` попадает в те же три случая: недостающая ветка — пустая, она проваливается со
старым окружением. Переменная, присвоенная только в ней, подчиняется соединению окружений:
использовать её после `if` можно, лишь если она была связана раньше.

**Соединение окружений.** Если проваливается несколько веток, их окружения соединяются:

- имя имеет во всех них одну версию — остаётся;
- версии разные — ветки возвращают её в кортеже соединения, после `case` вводится новая;
- имя есть не во всех — **ошибка компиляции**: присвоена только в части веток. В Python это
  `UnboundLocalError` на рантайме; здесь оно ловится раньше.

Веток, заканчивающихся `return`, соединение не касается: раз они не проваливаются, на
продолжающемся пути их имён нет.

### 4.4. Примеры

`if` без `else` посреди функции — соединение одной переменной:

```python
def index(start_from_0):
    i = 0
    if not start_from_0:
        i = 1
    i * 10
```

```erlang
index(S) ->
    I = 0,
    I@1 = case eel_rt:truthy(S) of
             true  -> I;
             false -> 1
         end,
    I@1 * 10.
```

Хвостовое ветвление — `case` само является значением:

```python
def classify(n):
    if n < 0:
        'neg'
    elif n % 2 == 0:
        'even'
    else:
        'odd'
```

```erlang
classify(N) ->
    case N < 0 of
        true  -> neg;
        false ->
            case eel_rt:mod(N, 2) =:= 0 of
                true  -> <<"even">>;
                false -> <<"odd">>
            end
    end.
```

Ранний `return` перед продолжением — диспетчер; внутри `rest` обычное соединение:

```python
def price(count, vip):
    if count <= 0:
        return 0
    total = count * 10
    if vip:
        total = total - 2
    else:
        total = total + 1
    total
```

```erlang
price(Count, Vip) ->
    case case Count =< 0 of
             true  -> {ret, 0};
             false -> {join}
         end of
        {ret, V} -> V;
        {join}   ->
            Total = Count * 10,
            Total@1 = case eel_rt:truthy(Vip) of
                         true  -> Total - 2;
                         false -> Total + 1
                     end,
            Total@1
    end.
```

Несколько имён — кортеж соединения:

```python
def g(c):
    if c:
        a, b = 1, 2
    else:
        a, b = 3, 4
    (a, b)
```

```erlang
g(C) ->
    {A, B} = case eel_rt:truthy(C) of
                 true  -> {1, 2};
                 false -> {3, 4}
             end,
    {A, B}.
```

`n < 0` и `count =< 0` обходятся без проверки на истинность: результат сравнения — всегда
boolean, и генератор это знает.

### 4.5. Лямбды и захват

Свободные имена лямбды — те, что она читает извне; они разрешаются на версию, текущую в точке
определения.

```python
def adder(n):
    return lambda x: x + n
```

```erlang
adder(N) -> fun(X) -> X + N end.
```

Захват по значению расходится с Python, где лямбда видит позднейшее переприсваивание (Р §2).
Моё предложение: имя, захваченное лямбдой или вложенным `def`, нельзя переприсваивать в той
же области — ошибка компиляции. Вопрос остаётся открытым (2.4).

### 4.6. Guard-ы

Guard-legal выражение (сравнения, `not`, арифметика) остаётся настоящим guard-ом Erlang.
Остальное опускается: тело выполняется, когда guard истинен, иначе пробуются следующие
ветки. Они повторяются под каждым вычисляющим guard-ом — плата за то, что продолжение
остаётся в хвосте.

```python
def pick(r):
    match r:
        case ('ok', n) if n % 2 == 0:
            'even'
        case ('ok', _):
            'odd'
        case _:
            'no'
```

```erlang
pick(R) ->
    case R of
        {ok, N} ->
            case eel_rt:mod(N, 2) =:= 0 of
                true  -> even;
                false ->
                    case R of
                        {ok, _} -> odd;
                        _       -> no
                    end
            end;
        {ok, _} -> odd;
        _       -> no
    end.
```

Ветвление без сработавшей ветки получает замыкающую `case _ -> erlang:error({case_clause, V})`.

### 4.7. Comprehensions

Истинность фильтра — guard-выражение, поэтому comprehension остаётся comprehension:

```erlang
[X * 2 || X <- eel_rt:iter(Xs),
          not (X =:= false orelse X =:= nil orelse X == 0
               orelse X =:= <<>> orelse X =:= [] orelse X =:= {} orelse X =:= #{})]
```

В OTP 29 фильтром может быть и вызов функции — проверено; на это можно опереться, если
минимальная версия OTP будет 26 или выше.

## 5. Рантайм `eel_rt`

Один модуль на Erlang с исходником в пакете: `eel/runtime/eel_rt.erl`.

- `truthy/1`, `add/2` (числа, бинарники, списки), `mod/2`, `floordiv/2`, `pow/2`, сравнения,
  `iter/1`, `range/3`, `zip/2`, `enumerate/2`, `join/2`, `print/1`, `str/1`.
- Дешёвые проверки (`truthy`) встраиваются в код места вызова; остальное — вызов
  `eel_rt:…`.

Что это даёт:

- исчезают зарезервированные имена функций (`eel_mod`, `_eel_pow`, `eel_print`…) —
  резервируется только имя модуля `eel_rt`;
- модуль и REPL выполняют один и тот же код;
- рантайм читается, тестируется EUnit и правится как обычный Erlang, а не как стена кортежей
  в `eel/backend.py:1345–1580`.

Как пользовательский код его находит: `eel build` компилирует `eel_rt` из исходника в ebin
проекта, если его там нет или исходник изменился; REPL — в кэш при первом старте. Пакет
остаётся чистым Python без готовых `.beam`.

## 6. Диагностика

`EelError(code, path, line, col, message)`. Правила:

- каждое исключение парсера Python переводится в `EelError` с файлом и строкой;
- известные ошибки `erl_lint` переводятся в сообщения; неизвестные сопровождаются словами
  «сгенерированный Erlang отвергнут — это ошибка компилятора» и позицией;
- внутренний сбой компилятора даёт `eel: internal compiler error at path:line` и трейсбек в
  файле журнала, но не на терминале;
- за один запуск собираются ошибки всех модулей, а не первого не собравшегося.

Инвариант проверяется фуззингом: на любом входе компилятор возвращает либо формы, либо
`EelError` — ничего третьего.

## 7. Сборка

### 7.1. Проект и зависимости

Файл проекта не нужен, приложение называется по каталогу — как сейчас. Манифест расширяется:
для каждого модуля хранятся хеш исходника, список импортов и экспортируемые функции с
арностями.

- Изменившийся модуль пересобирается вместе со всеми, кто от него зависит, транзитивно.
- Модули компилируются в порядке импортов. Вызов `f(1)` для `from a.b import f`, где `a@b` —
  модуль проекта, проверяется по индексу: `module a.b has no function f/1 (has f/2)`.
  Вызовы библиотеки Erlang не проверяются.
- Каталог без `src/` — ошибка, а не пустой `.app`.

### 7.2. Build server

Сервер нужен ради цикла «правка → сборка» без старта интерпретатора и VM. Его форма с нуля:

- **Один публичный процесс.** Build server — единственная точка входа; Erlang-компилятор —
  его дочерний процесс по каналу stdin/stdout, перезапускается, если умер. Второго сокета и
  отдельного демона нет.
- **TCP на 127.0.0.1.** Порт, pid и случайный токен лежат файлом в каталоге кэша; клиент
  предъявляет токен. Работает на всех трёх системах по одному коду.
- **Поток на соединение.** Сборка идёт под блокировкой, но статус отвечается, пока она идёт;
  ping больше не зависит от длительности сборки.
- **Старт под исключающей блокировкой.** Второй клиент ждёт endpoint-файл, а не поднимает
  второй сервер.
- **Клиент, который ушёл, безвреден:** каждая запись в сокет защищена.
- **Устаревший компилятор.** Сервер сверяет отпечаток файлов пакета на каждом запросе и при
  изменении отвечает `restart` и выходит; клиент перезапускает его и повторяет запрос.
- **Остановка убирает только свои файлы** — сверяется токен.

Но строить его я бы последним. Сначала — путь «escript внутри процесса»: он медленнее
(порядка полсекунды на сборку), зато в нём нечему падать, и он остаётся эталоном, с которым
сверяется сервер.

### 7.3. Команда

- `eel build [DIR]` — как сейчас;
- `eel run DIR MODULE FUNCTION [АРГУМЕНТЫ]` — собирает и запускает функцию модуля с
  проставленным путём кода; сегодня для этого нужна строка запуска `erl` вручную;
- `eel shell` — REPL из ноутбука в терминале;
- `eel daemon start|stop|status`.

## 8. Ноутбук и REPL

**Ядро вместо хука.** Подкласс `ipykernel` строк на сто, который объявляет
`language_info.name = "python"`: подсветка, автодополнение и LSP в Jupyter выбираются по
этому полю, так что цель из `specs/notebook.txt` — «ячейки остаются текстом Python» —
достигается без хука. Заодно уходят дефекты Р §6: пустая ячейка не выполняет предыдущую,
ошибка помечает ячейку, без расширения ячейки не исполняются CPython.

Это расходится с прежней позицией автора («не хочу писать ядро»). Аргумент за: хук и есть
источник найденных дефектов, а ядро — это тот же код в более прямом месте.

**REPL.** Транспорт — ETF в обе стороны вместо текста: одна сериализация с модульной сборкой.
Оценка каждой ячейки идёт в отдельном процессе под мониторингом; прерывание убивает процесс,
а не сессию — зависший `receive()` перестаёт быть тупиком. Значения печатаются синтаксисом
eel (`'ok'`, `"hi"`, `(1, 2)`, `{'a': 1}`), а не терминами Erlang.

**Одна модель для модуля и ячейки.** Ячейка — тот же блок. `def` в ячейке — вложенное
определение: именованный `fun` в переменной. Декораторы в ячейке применяются сразу, как у
вложенных `def`, — механизмов декораторов становится два вместо трёх: для функций модуля
(`persistent_term` + `-on_load`) и для локальных определений.

## 9. Проверка: оракул — CPython

- **Дифференциальные тесты.** Программы, валидные в обоих мирах, лежат в
  `tests/differential/`; каждая прогоняется под CPython и под eel, печатный выход сравнивается.
  Каждое семантическое решение закрепляется таким тестом: истинность, ранний `return`,
  соединение окружений, операторы. Отличия по замыслу (атомы, процессы) проверяются вручную
  написанными тестами.
- **Снимки.** Для каждой конструкции — ожидаемый Erlang в `tests/snapshots/`: lowering читается
  и ревьюится как код, а не как кортежи.
- **Рантайм** — EUnit по таблицам истинности и операторов.
- **Сборка и сервер** — на фейках: медленный escript, молчащий клиент, ушедший клиент, второй
  сервер. Гонки из Р §5.2–5.3 воспроизводятся детерминированно.
- **Фуззинг** — инвариант из §6.
- **ruff и CI** (Linux, Windows) с первого коммита: `F811` ловил бы дубли `eel/backend.py`.

## 11. Переход от текущего кода

С нуля — не значит с пустого места. `eel/etf.py` и `eel/term.py` хороши как есть;
`eel/eel_compile.escript` остаётся с лучшим переводом ошибок; frontend сохраняет примерно
половину — разбор выражений; из backend — маленькие построители форм и таблицы методов.

Порядок, при котором тесты остаются зелёными после каждого шага:

1. Новый оракул: дифференциальные тесты с CPython и снимки — на текущем языке.
2. Frontend: убрать присваивание с паттерном и классы, перейти на голые кортежи.
3. Генератор: `gen_block` с окружением, соединением и диспетчером; ранний `return`; `if` как
   оператор. Заменяет `_Gen` для тел функций.
4. `eel_rt.erl`; истинность; guard-ы.
5. Сборка: граф импортов, индекс, `eel run` и `eel shell`.
6. Ядро ноутбука. Затем build server.

## 12. Чего я сознательно не предлагаю

- **Собственный парсер.** `ast.parse` бесплатен и следует за Python; цена — правило атомов
  поверх токенов.
- **Статические типы.** Аннотации остаются документацией; проверка — сторонними средствами.
- **Переписывание на Rust или «static python».** Проблемы проекта не в языке реализации.
- **Генерацию BEAM напрямую, минуя abstract forms.** `compile:forms` закрывает линтирование,
  оптимизации и отладочную информацию.
- **Циклы, классы, исключения.** Каждое из них — отдельное решение, а не следствие
  «подмножества Python».
